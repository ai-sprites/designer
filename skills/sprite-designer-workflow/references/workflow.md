# Designer 有序工作流

## 证据与快速迭代

证据优先级依次为：当前请求与验收条件、用户认可的视觉参考、已验证的产品行为、项目设计基线、适用于本界面的已确认技术约束与真实项目组件，最后才是个人偏好。冲突说明来源、影响及需要的决定，不能把观察或建议当成批准。

项目或用户已选择快速迭代时，设计本次用户旅程中最小而完整的改动，检查受影响切片及最近的已验证模式；复用布局、组件、内容和导航。只覆盖主要路径、关键失败与恢复、实际受影响的响应式及无障碍行为，不构造理论状态/视口矩阵。单次改动不自动扩展到设计系统、token 集、通用组件 API 或全站改版。

baseline、持久设计说明、原型、Figma 和高保真比较按明确请求以及评审、交接、持久决定的需要产出。用户明确要求建立或更新 baseline 时，即使改动很小也必须实际保存；快速模式不能成为省略交付的理由。已有文件优先局部更新。

## 17 步工作顺序

1. **读请求和已确认参考。** 读取当前请求、验收条件、项目规则与已存在的产品/资料索引，沿用资料的真实位置，不要求为设计新建一套。需求、参考、架构或开发方案不在本地时，按已有来源约定通过 bridge 获取明确版本，保留来源；按入口的交接规则处理跨仓 baseline、spec 和附件。
2. **独立确认职责与缺口。** PM / BA 或 Architect 未接入时，使用已确认请求和现有证据继续；仅在缺少完成设计必需的产品或技术决定时提问，不代写其他角色产物作为替代。
3. **检查最小有用界面切片。** 检查应用壳或路由、共享布局与组件、主题或全局样式、一个相近界面、国际化以及相关测试/故事。记录实际看到的项目行为；新项目没有现状时使用已确认方向，不把计划写成现有实现。
4. **读取并维护项目设计基线。** 完整读已有 baseline；需要保留稳定项目共性或用户明确要求时，用完整 [设计基线模板](../assets/templates/design-baseline.md)创建真实文件。只在证据变化或明确要求下更新相关内容，保留已有自定义和人工段，人工维护段逐字保护。无默认位置时用 `docs/design-baseline.md`；同一项目保持一个跨功能主源。新项目可记录“已确认方向，待实际渲染验证”、来源和影响，不能伪称已观察到的事实。
5. **应用本界面的技术约束。** 从项目已确认约定、真实代码与开发方案中识别适用于本界面的约束。已观察到的实现和待定建议不等于已确认要求；未确定技术栈时保持技术中立，记录可实现性要求，由开发角色结合项目选择框架与库，不代做技术或架构决定。
6. **定义体验与实际状态。** 明确用户从哪里来、要获得什么结果、用户旅程、信息顺序、主要动作、相关视口、数据条件以及实际可能出现的加载、空、部分、错误、成功状态，说明重要转换与恢复。
7. **设计正常且完整的界面。** 按已确认行为和证据最充分、可逆且不需要人作主的假设完成设计。PRD/故事依赖、假设和待确认事项与产品内容、状态和布局分开，不把它们做成横幅、占位卡片、禁用控件或额外步骤，除非它们确实是用户应见的行为。需要人的决定立即问，继续不受影响部分。
8. **用独立层放有锚点的审阅标注。** 审阅者需要局部背景时，可把 `!` 标记锚定到具体界面元素，弹层用白话说明事项、来源或负责人、依赖它的后续工作。标记与弹层必须在独立审阅层，位于产品布局之外；隐藏或移除整层后，界面尺寸、间距、层级、文案、交互、状态、无障碍与实现要求均保持不变。
9. **把无法独立分层的备注放进 spec。** 无具体界面锚点，或工具不能保持标注独立时，将备注放入功能设计说明的“仅供审阅的标注”表，不放进产品 UI。保留标记、画面及锚点、类型、白话说明、来源或负责人、后续依赖六列。
10. **使用真实可信的代表内容。** 用符合已确认业务场景、目标用户熟悉的普通语言。名称、日期、金额、状态、标签与消息跨画面一致。在 spec 的“界面内容”中标明草稿或演示数据，不在产品 UI 加内部标签。避免真实个人/生产数据、lorem ipsum、含混占位、口号和自造术语。
11. **区分备注与必需的人的决定。** 只有当前设计不依赖人的决定且未知非阻塞时才用审阅备注；非阻塞备注本身不使设计成为 `Blocked`。任何受影响 UI 要定稿而必须由人决定时，立即提问，只暂停相关部分，得到实际回答后写入决定记录，不以备注替代决策。
12. **按项目证据复用组件。** 顺序是同类已验证局部模式、项目现有组件、现有基础组件的组合、已批准的体系扩展，最后才是附简短理由的功能局部组件。记录真实来源、相关属性/状态/素材与新增理由，不编造组件 API，也不擅自重建设计系统。
13. **覆盖受影响的响应式与无障碍。** 核对实际相关视口的布局变化、键盘与焦点行为、标签、错误、阅读顺序、内容状态、对比度、动效及项目国际化/格式习惯。必要信息不能只依赖颜色或悬停；说明实现必须保持的约束、可灵活处理之处和不得推断的细节。
14. **实际渲染并对照。** 视觉工作渲染受影响视口，与认可的参考或相邻产品界面对照，根据观察到的层级、间距、溢出、裁切、对比度和状态差异迭代。能隐藏标注时同时检查干净画面。记录真实截图/视口、运行或操作结果；未运行、访问失败或未检查如实写出，不能把静态阅读当渲染检查。
15. **保存功能说明和必要基线。** 用户要求、持久设计决定、评审或实现交接需要时，按完整 [设计说明模板](../assets/templates/design-spec.md)实际保存，默认 `docs/artifacts/<feature-id>/design.md`；稳定项目共性写入共享 baseline，功能说明引用它。核对意图/验收、体验与状态、内容、标注、响应式、组件素材、无障碍、实施约束、视觉证据、可逆假设和决定记录，明确已确认、草稿、未验证或受阻及影响。不适用项诚实标明；不能只给概述代替要求的文件。
16. **按条件完成 Figma 工作。** 仅当用户请求 Figma 工作或提供认可的 Figma 参考时使用。按下节检查目标、权限、组件、布局与成品，只有实际读取或修改后才记录真实文件及节点信息；没有权限不能编造访问或产物。已有目标与授权够用时直接工作，不重复确认。
17. **用真实证据交接。** 只有存在认可的参考和相同视口下的实际渲染对照，才可声称像素一致或高保真一致。按验收条件核对交付覆盖，提供真实画面/原型、baseline 和功能 spec 的链接、仓库、路径、依据版本，以及检查结果和未完成项。跨 Git 分别选入基线、说明和必需附件，核对可获取提交状态，不把尚未提交/推送的本地文件说成远端可读。

## 使用 Figma 时

- 编辑前核对真实目标文件、页面、画面、状态、视口及所需访问权限；已有信息充分就直接工作。遇到真实权限缺口说明具体影响，继续不依赖该权限的设计部分。
- 有经认可的项目组件、样式和变量时复用。代码采用某个 UI 系统，不代表存在唯一对应 Figma 库，也不代表当前账号可以使用它。
- 可复用组合使用适合的自动布局，按有意义的区段逐步构建与检查。
- 审阅标注独立于产品自动布局；隐藏标注层后验证干净画面的内容、布局、状态与无障碍表达完整。
- 完成后实际检查画面的信息层级、间距、溢出、裁切、对比度及必要状态，按观察到的问题修正。
- Figma URL、文件 ID 或节点 ID 必须来自实际读取或修改的结果；不能从期望目标编造完成记录。

## 产物刷新时的保护

模板是新文档的完整起点，不是覆盖已有业务文档的命令。刷新前完整读取现有文件，确认项目约定和本次变更证据；逐段更新受影响事实，保留旧文件中仍适用的自定义章节、额外表格字段、手写说明与链接。人工维护说明段（含原 `Human-curated notes` 或项目自定义等价段）逐字保留，除非用户明确要求修改该段。发现来源冲突时记录差异并请维护者决定，不凭个人偏好重生整份基线。读取外部主源只建立引用，不自动回写或升级它。
